## 修改协议的七个问题

### 1. 根因

| 问题 | 根因与修复边界 |
| --- | --- |
| 输入法跨应用回写 | 新前台应用不需要切换时没有产生新 generation，旧应用的确认/重试链仍能写系统输入法；应用上下文变化必须使旧链失效。 |
| 反向 BLE 丢样本 | 服务端提前替换仍在有效期内的 nonce，客户端旧读取结束时未继续处理新 challenge；保留未消费的有效 challenge，并保证客户端能继续处理等待中的 challenge。 |
| UU 策略失败后不再重试 | 把请求尝试误当成应用成功；完成标记跟随 Helper 确认状态，失败按退避重试，用户恢复/抑制状态优先。 |
| Helper 获批后半启动 | 注册与批准失败后只恢复了轮询，没有完成监控初始化；成功准备服务后补齐运行生命周期。 |
| 恢复覆盖手动开屏 | 非强制恢复要求当前电源状态与原始状态完全一致才跳过；已开屏时尊重当前状态，明确的强制恢复仍还原原始状态。 |
| 搜索关闭抢设置焦点 | 用进程 active 状态代替面板的焦点归属；关闭前记录其他 key window 是否已接管，接管后不归还外部应用焦点。 |
| 图标缓存内存峰值 | 完整读取后才限制大小；读取前检查文件大小，实际读取也设上限，覆盖检查后文件增长的情况。 |

- 修改前检查各文件历史和仓库 Revert 记录；保留显示恢复 journal、协议兼容及配置 append-only 约束。

### 3. 旧修复为什么不彻底

旧实现分别覆盖了新切换任务、常规快速 BLE 回调、Helper 已可用、策略成功、
原始电源状态为 on，以及关闭搜索时没有其他本应用窗口接管的正常路径。
本次补齐无需产生新操作的上下文变化、慢回调、批准后恢复及失败后的状态出口。
缓存原有测试只证明最后丢弃超大文件，未证明读取之前就拒绝。

### 4. 受影响功能

自动/手动输入法切换与重试、反向 BLE 存在采样、UU 显示器策略与 Helper 准备、
崩溃恢复和显式亮屏、快捷搜索中文输入与焦点归还、图标缓存命中和读取。
当前分支尚未包含 main 的搜索 IME 激活代码，因此一并带入这部分必要行为，
并增加异步输入上下文激活前的 key-window 校验；不调整界面布局和设计令牌。

### 5. 必跑测试

由 `python3 Scripts/regression-plan.py --mode local` 选择，并运行
`bash Scripts/run-regressions.sh`；补充输入法切换及协议包的反向存在测试。
修改的测试文件自身声明的套件也随选择器执行，包含任务开始前已有的测试改动。

### 6. 新增测试

- 输入法旧上下文失效、BLE challenge 生命周期和慢读取继续处理。
- UU 请求失败后的再次尝试、有效完成状态、Helper 批准后监控恢复及用户抑制保护。
- on/standby/off 原始状态下，手动开屏不被崩溃恢复覆盖；强制恢复仍还原原始状态。
- 搜索关闭后保留设置焦点、外部应用接管后不抢焦点、会话只恢复一次。
- 超大缓存读取前拒绝、检查后增长仍有界、恰好达到上限仍能读取。
